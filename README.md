# EvoSupplement

**Interactive supplementary material framework and authoring studio for comparative protein evolution.**

EvoSupplement combines browser-based editors, a project generator, and publication viewers for studies that integrate protein sequence, multiple sequence alignments, three-dimensional structure, genomic context, phylogeny, biological networks, taxonomic distributions, and protein domain architectures.

The source repository now opens as **EvoSupplement Studio**. Its root page is an authoring dashboard that links to the Project Builder and the six module editors. It is intentionally different from the home page of a paper supplement generated by the Builder.

## Studio and publication projects

EvoSupplement has two distinct contexts:

| Context | Root page | Audience |
|---|---|---|
| Source repository | EvoSupplement Studio | Authors preparing and packaging supplementary material |
| Builder-generated ZIP | Manifest-driven publication portal | Readers exploring the supplementary material of one paper |

The Studio root does not render a paper manifest. When the Project Builder creates a ZIP, it copies a dedicated publication-portal template into that new project and generates a matching `manifest.js`. Publishing the generated ZIP therefore opens directly to the paper title, authors, sections, figures, tables, datasets, and links.

## Authoring tools

| Tool | Purpose |
|---|---|
| [EvoSupplement Project Builder](builder/README.md) | Creates paper metadata, ordered sections, regular files, HTML packages, interactive figures, the publication manifest, documentation, citation metadata, and a GitHub Pages-ready ZIP. |
| [Protein Structure and MSA Editor](protein-viewer/README.md) | Loads PDB or mmCIF structures, associates chains with MSA references, captures residue selections or imports user-created Mol* selection components, creates compatible annotation YAML, and previews the publication scene. |
| [Gene Neighborhood Editor](neighborhood-viewer/README.md) | Loads standard TSV or compact architecture neighborhoods, curates domain display names and colors, ranks domain frequencies, and exports YAML dictionaries plus a normalized TSV. |
| [Phylogeny Editor](phylogeny-viewer/README.md) | Authors publication-ready Newick figures with selected support markers, saved roots, colored clade groups, three layouts, optional TSV labels, and a generated phylogeny YAML without changing the source tree. |
| [Network Editor](network-viewer/README.md) | Aggregates undirected relationships, filters by summed edge count, compares Louvain and Leiden communities, rearranges nodes, and generates node and color YAML files. |
| [Taxonomy Sankey Editor](taxonomy-sankey-viewer/README.md) | Reconciles protein TaxIDs, freezes resolved lineages, controls taxonomic ranks and compression, curates labels and colors, and exports an offline publication Sankey. |
| [Protein Domain Architecture Editor](domain-architecture-viewer/README.md) | Renders one-row-per-domain TSV files, compares true-length, normalized, and compact architectures, and curates domain names, colors, shapes, labels, sorting, grouping, and metadata hover. |

## Recommended workflow

1. Serve the source repository through HTTP and open the Studio home page.
2. Use one or more module editors to prepare and validate viewer-specific files.
3. Open the Project Builder.
4. Enter the paper title, authors, description, journal information, and DOI.
5. Create ordered sections and add files, HTML packages, links, placeholders, or interactive modules.
6. Validate the project and download the generated ZIP.
7. Extract the ZIP, preview its publication portal locally, and publish the extracted project with GitHub Pages or another static host.

## Common module pattern

Every viewer follows the same organization:

| Folder | Purpose |
|---|---|
| `shared/` | JavaScript and CSS used by every page in the module. |
| `editor/` | Author workspace for local uploads, validation, curation, preview, and generated files. |
| `figure1/`, `figure2/`, and so on | Reader-facing publication instances that load their data automatically. |
| `config.js` | Figure-specific title, paths, defaults, and module settings. |
| Data subfolders | Structures, alignments, annotations, trees, edge tables, dictionaries, and other scientific inputs. |

Editors and publication figures intentionally have different interfaces. Editors may expose file selectors and authoring controls. Publication pages should open directly for readers and normally contain no upload or YAML-generation tools.

## Project Builder

Open `builder/` from the Studio page or directly through an HTTP server. The Builder supports:

- paper metadata and ordered authors;
- arbitrary sections and ordered items;
- uploaded files and self-contained HTML pages;
- ZIP-packaged HTML pages with an `index.html` entry point;
- external links and coming-soon placeholders;
- all six implemented EvoSupplement modules;
- input validation and predictable output paths;
- packaging only the modules used by the project;
- a generated manifest, README, deployment guide, citation file, license, and GitHub Pages workflow;
- reopening a previously generated ZIP through `evosupplement-project.json`.

A generated project receives the publication portal from `builder/templates/publication-portal.html`, not the Studio root page. This separation prevents authoring tools from replacing the reader-facing supplement.

## Generated publication portal

The root of a Builder-generated project contains:

- `index.html`, the publication portal renderer;
- `manifest.js`, the paper metadata and ordered content definition;
- only the viewer modules selected by the author;
- uploaded files and scientific inputs;
- `README.md`, `DEPLOYMENT.md`, `CITATION.cff`, and an optional license;
- `.nojekyll` and `.github/workflows/pages.yml`;
- `evosupplement-project.json` for reopening the project in the Builder.

The generated portal reads `manifest.js` and creates:

- the supplement title and citation information;
- an optional description and DOI link;
- section headings;
- cards for viewers, files, tables, images, datasets, documents, and external resources;
- non-clickable coming-soon cards for unfinished items.

### Manifest structure

A publication manifest has `paper` metadata and an ordered `sections` array.

Common paper fields are:

| Field | Purpose |
|---|---|
| `title` | Supplement or paper title shown on the portal. |
| `authors` | Author list or citation text. |
| `description` | Optional explanatory paragraph. |
| `journal` | Journal, venue, or preprint server. |
| `year` | Publication year. |
| `doi` | DOI without the DOI website prefix. |

Each section contains ordered items. Common item fields are:

| Field | Purpose |
|---|---|
| `id` | Optional internal identifier. |
| `title` | Card title. |
| `description` | Short reader-facing summary. |
| `type` | Badge category such as `viewer`, `pdf`, `image`, `table`, `dataset`, `doc`, or `external`. |
| `href` | Relative project path or complete external address. |
| `external` | Optional flag that forces a new browser tab. |

A blank `href` produces a visible, non-clickable coming-soon item.

## Manual publication-project maintenance

The Builder is the recommended path, but generated projects remain ordinary static repositories. Authors may later edit:

- `manifest.js` for portal-only content changes;
- a figure folder's `config.js` for initial viewer settings;
- the scientific files inside that figure folder;
- static files, external links, and documentation.

The shared JavaScript, shared CSS, and publication `index.html` templates should normally change only when updating the framework version.

## Local testing

Use an HTTP server because browsers may block local TSV, YAML, FASTA, PDB, mmCIF, or Newick loading under `file://`.

From the source repository:

```bash
python3 -m http.server 8000
```

Then open:

```text
http://localhost:8000/
```

This opens EvoSupplement Studio. The Project Builder is at `/builder/`, and each module editor is under its viewer folder.

For a generated paper project, run the same command from the extracted project root. Opening `/` then shows that project's manifest-driven publication portal.

## Deployment

Both the Studio source repository and generated publication projects are static sites. They can be hosted with GitHub Pages or another static service.

Before publication, confirm that:

- filename capitalization is exact;
- every local path works from the page that uses it;
- every publication viewer loads automatically;
- large files comply with the host's limits;
- external datasets use persistent links;
- private or unpublished data are not included unintentionally;
- the extracted contents, not the ZIP file itself, are placed at the repository root.

## Publication checklist

- Paper title, authors, venue, year, and DOI are final.
- Portal sections and item order match the supplement.
- Every visible card has an accurate title and description.
- Every non-empty local and external link resolves correctly.
- Interactive figures load without requiring reader uploads.
- Structures, alignments, trees, annotations, neighborhoods, and networks are final.
- Source files needed for transparency are downloadable.
- Authoring controls remain in `editor/`, not in reader-facing `figureN/` pages.
- The published release is archived and citable.

## Example content

The source repository contains example editor data, figure configurations, and an example `manifest.js` for development and testing. These files demonstrate formats and interfaces; they are not final scientific material for a paper.

## Citation and attribution

A formal software citation can be added when EvoSupplement receives a versioned release or archival DOI. Paper projects should also cite the scientific data sources, structure repositories, analysis software, and external libraries used by their modules.

The protein viewer uses Mol* for molecular visualization. The phylogeny, network, and taxonomy viewers use browser-native SVG rendering. Viewer inputs and Builder uploads are processed locally in the browser unless an author intentionally links to an external resource.
